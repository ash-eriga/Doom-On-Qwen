The [Qwenputer](https://github.com/divagr18/qwenputer) CPU gets a much bigger program: the Doom
engine. The port is built for the [linuxformer](https://github.com/itsrealranky/linuxformer) LX
machine, an RV32IM + Zba core, and runs inside Qwen3.5-4B as a stream of verified trace tokens.

| clip | frames | verified | GPU | tokens |
|---|---|---|---|---|
| **192x120** | 116 (6-121) | 116/116 byte-exact | A100 40GB, 19,109 tok/s | 106.1M | ~10 CU |
| 96x60 | 116 (6-121) | 116/116 byte-exact | L40S, 17,700 tok/s | 64.7M |

Both clips are the same 11.6 s of E1M5 at two render sizes. The larger one needs 2.03x the
instructions per frame for 4x the pixels, because the engine dominates and drawing is the minority
of the work. `packed.pt` is per-build: different `.text` bytes are a different weight set.

The preview above is the 192x120 run. The 96x60 run is at the same frames, in
[`docs/doom-e1m5-in-weights-96x60.webp`](../docs/doom-e1m5-in-weights-96x60.webp).

Both previews are lossless WebP, generated by nearest-neighbour upscale from the frames
themselves; 116 of 116 decoded frames are pixel-identical to the mp4s in
[`ops/work/preview/`](ops/work/preview), which are the originals.



## What "verified" means

Two machines propose and check the same trace:

- The **reference machine** ([`lx.ref.Machine`](https://github.com/itsrealranky/linuxformer), the
  executable spec) proposes tokens and holds the ground RAM.
- The **circuit** verifies that stream as chunked prefill. It is never allowed to drift more than
  a bounded window ahead of the verified frontier, so a checkpoint can only be saved with both
  machines at the same instruction.

A frame is written only once every token that produced it has verified. The comparison that
matters is against `fastemu-lf`, a native C emulator that renders from the same ELF and the same
key schedule (`sched.txt`):

```bash
cc -O3 -o fastemu-lf port/native/fastemu-lf.c -lm
./fastemu-lf doom-lf.elf --wad doom1.wad \
  --fbp-sym DG_ScreenBuffer --fc-sym qwen_frame_count \
  --keys-sym qwen_key_state --demo-sym qwen_demo_enabled \
  --frames 130 --script sched.txt \
  --dump-every 1 --dump-from 6 --dump-to 121 --dump-dir ref --guest-out none
```

Frames compare byte for byte on the PPM payload. The 116 frames in both clips are exact.

## What is not true

Two claims from earlier sessions were wrong, and both are corrected in [`ops/work/STATE.md`](ops/work/STATE.md):

- **It is not 0-wrong.** The rate depends on the build: 192x120 misses 450 of 106.1M (~4.2e-6),
  96x60 misses 1,023 of 64.7M (~1.6e-5). Frames are unaffected because the errors are
  one-value-off pairs (`65536`/`65537`, `65557`), which look like a rounding boundary in the fast
  path. The circuit does not predict every token, and the smaller build predicts worse.
- **The A100 is not slower than the L40S.** An intermediate reading said 11,541 tok/s on A100;
  that run had mismatched artifacts. With the correct pair, A100 is 19,109 against L40S 17,700.

Two more things worth knowing before quoting numbers:

- **The clips are not 320x200.** They are 96x60 and 192x120 at `screenblocks=11`. The frames are
  read as a linear prefix of the 320x200 buffer, not a strided crop.
- **Tokens per instruction is build-specific.** 192x120 runs at **1.606**, not the 1.5087 constant
  from earlier notes. That difference is why a 95M-token budget stops at frame 119.

## Reproducing it

The emitted circuit is per-build: different `.text` bytes mean a different weight set, and a
checkpoint only resumes on the weights it was saved with. Emit first, on CPU, about 11 minutes:

```bash
python ops/work/kaggle/run_kaggle.py --emit --data <dir with doom-lf.elf> --lxsrc <lxsrc> --work <out>
```

Then rent a GPU. `packed.pt` is 4.08 GiB, so a 24 GB card is enough; an 80 GB A100 buys nothing
here.

```bash
colab new -s doom192 -gpu A100
colab exec -s doom192 -f ops/work/runs/colab_setup.py --timeout 1700
colab exec -s doom192 -f ops/work/runs/colab_run.py --timeout 9000 \
    --env HF_TOKEN=... --env HF_DATASET=<owner>/<dataset> \
    --env SET=192 --env RESUME=0 --env HOURS=3.0 --env NTOK=95000000
```

`ops/work/runs/run-192x120.ipynb` is the same flow as a notebook, including the `fastemu-lf`
comparison.

## Status

Two 116-frame clips delivered and verified. The engine runs; it does not play well. The
`lightlevel` bug in `STATE.md` section 12 leaves the player in the line of fire, so the demo dies
early. Nothing below that is blocked on the circuit.
